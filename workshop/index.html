Prototype. The rules are final; the hard part is not built.

What is actually being tested here

There is already a bot on my profile that takes an issue from anybody on the internet, sanitises it, writes it into my README, thanks the author and closes the issue. No human is involved at any point. That machinery works, and it has been attacked with thirteen different flavours of hostile input without breaking.

So the question is what else you could point it at. A guestbook is a wall. This is the same machinery pointed at a world: someone opens an issue titled move: north, a workflow takes one step, redraws the picture and closes the issue. Do that for a week and the internet has walked the robot across the floor to the hammer, one stranger at a time.

The interesting part is not the maze — mazes are trivial. It is that a document you thought you were only reading turns out to be a thing that people are playing, slowly, over days, without ever meeting each other. That is the reaction I am building for.

What is not solved

  • One person could just walk him. The rate limit has to be per author, and GitHub gives me the author for free — but the moment I enforce it, the first thing a visitor sees may be "you already moved today," which is a worse first impression than a maze.
  • A blocked move still burns a turn. That is deliberate: it means walking him into a wall achieves nothing, so there is no reward in griefing. Whether it also feels unfair to someone who guessed wrong is a different question and I do not know the answer yet.
  • The README needs a picture, not this. The panel on the right is monospace because monospace is cheap and this is a prototype. The real frame is an image a workflow has to render and commit on every single move, which is a binary in git history several times a day — the exact thing I refused to do for the robot GIF.
  • Concurrency. Two issues opened in the same minute are two workflow runs racing the same file. Solvable with a concurrency group, untested.

Offcuts

Approaches that were wrong. They are here because the reasoning is usually more useful than the thing that shipped, and because a portfolio with no failures in it is not a portfolio, it is an advertisement.

  • A colour ramp on the engraving. The obvious way to colour a monochrome plate is to map its luminance through a gradient. It does not work: hatching averages into the middle of the range almost everywhere, so nearly every pixel lands on the same mid stop and you get the original picture under a purple filter. What replaced it treats the plate as ink and paper and decides where the light is separately.
  • The circular portrait frame. It looked like a portrait, which was the point, right up until the lightning grew into an arch and the mask ate the corners it was arcing through. The picture is a rectangle and it gets to stay one.
  • A 3.6 MB GIF. One 256-colour palette across a graded storm sky forces the encoder to dither, and dithering a gradient that the smoke is already warping is close to maximum entropy. The same eight seconds is 746 KB as an animated WebP, which GitHub renders in a README perfectly well.
  • A test that could not fail. I checked the animation looped seamlessly by comparing the first frame against the frame one full loop later. The drawing function wraps its own clock, so those are the same call — it was comparing a frame with itself and reporting a perfect score for a visibly broken loop. This one is the most useful thing on the page: a test you have never watched fail is not evidence.
